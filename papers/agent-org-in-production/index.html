The Agent Organization in Production

Inboxes, gates and decision windows: how a Claude Code agent org actually runs a start-up, what broke when it ran too hot, and what the first week after the reset measured.

Felipe MolinoFounder, CorkAI6 November 2026Follows Part I and Part II

Executive summary

  • Part I set the method (control areas, levels, evidence). Part II set the decision rights. Part III is the operations manual: how the agents talk, what they can't touch, when I decide, and what it costs.
  • The first setup worked and was unaffordable. About 20 role chats, all on Opus, messaging each other around the clock, merged 233 pull requests in one week. They also used a full week's Claude plan in about two days.
  • The cost was memory, not work. Long chats re-reading their own history made up most of the bill. Every message between agents woke another long context.
  • The reset, on 2 November: 8 standing chats (2 on Opus, 6 on Sonnet), short per-ticket build sessions, one-line asks in files instead of messages, a decision queue I see twice a day, and plain scripts for anything that doesn't need a model.
  • First four weekdays after the reset: API-priced work fell from $6,350 to $438, Opus fell from 99% to 55% of cost, and cache reads from 55% to 32%. Merged pull requests fell too, from 233 in the peak week to 37 so far this week. Part of that drop is deliberate, and part is still being worked out.

The agents were never the bottleneck. The expensive parts were their memories, their conversations with each other, and their questions to me.

01Where this starts

Part I described how to score and gate AI-built software. Part II described which decisions stay with me and what evidence each one needs. Both assumed the organization of agents underneath simply ran. This paper is about that organization: the chats, the files they share, the rules they can't break, and the clock they run on.

CorkAI is built and run by Claude Code chats on one PC, each with a role: product, development, QA, security, marketing, data and so on. I am the only person. Everything below comes from that setup's own logs, its usage files and the GitHub history of the main repository.

02The before: one very productive, very expensive week

In the week of 26 October the setup was at its largest: about 20 role chats (a COO, Strategy, a Chief of Staff, Product, a Dev Lead and three more developers, QA & DevOps, InfoSec, UX, Marketing, Marketplace, Wine Data, Research, Analytics, Finance & Ops, Revenue, Investor Relations, HR), plus four or five scheduled runs a day. Every one ran on Opus. They ran about 21 hours a day and coordinated by messaging each other.

What the audit found

The cost did not come from writing code. It came from context. Fifty-eight percent of the cost was cache reads: long chats re-reading their own history on every call. One chat made 1,528 model calls in a day and read 767 million cached tokens. The Chief of Staff rebuilt its action page 193 times in about 17 hours. Shared files had grown to 463 KB (the security log) and 214 KB (the decisions log), and every chat that opened them paid to read them again.

Three habits multiplied it:

  • Agents messaging agents. Each nudge woke a long context on the other side. A routine "did you see this?" could cost more than the work it asked about.
  • The most capable model for everything. Monitoring, data pulls and status checks ran on Opus. On API list prices Sonnet costs about half as much and Haiku about one fortieth.
  • Questions at any hour. Decisions reached me as a stream, and the chats waited on each answer.

03Files, not messages: the inbox process

The reset, recorded as an architecture decision on 2 November, rests on one idea: agents coordinate through small files, not conversations. A file costs nothing until someone reads it, and it is still there after a chat forgets.

One line per ask

Every area has an inbox file. Any chat that needs something from another appends one line to it:

DateFromAskDueLink
3 NovChief of StaffRefresh your handoff file and move any plan or decision that lives only in the chat into a filenowthe operating model

A chat reads its inbox at the start of each work block and moves cleared items to a "done" list. Direct messages are kept for four cases: production down, a security incident, money moving, and the chat reset itself.

The decision queue and two packs a day

When a chat needs me, it doesn't ask me. It writes one item to a shared queue: the question, the options, its recommended pick, and what a yes or a no would unblock. Only the Chief of Staff turns that queue into what I see, which is a decision pack at 7:30 and at 4:30 Eastern. Each pack carries a short standup (yesterday, today, blockers, budget pace by project) and a numbered list of decisions with recommendations. I answer in one line, for example "1 yes 2 skip 3 yes". Between windows the chats keep working on anything that isn't blocked.

Defaults with an undo

The first version of the reset said that unanswered items wait. Within hours that proved too slow: everything stopped for my approval. The same afternoon the rule changed to "default and go". If I haven't answered by the next window, and the item is reversible and not one of my keys (section 04), the Chief of Staff marks it applied by default and the owning chat proceeds. Every default is one line in a defaults log with a one-line undo, and it appears in the next pack under "done by default". Packs now list only my keys and real taste calls as decisions.

Handoff files and memory

Every standing chat keeps a handoff file under 3 KB: goal, work in flight, next step, open asks, links. A fresh chat that reads its charter, its handoff and its inbox can pick up where the last one stopped. On 2 November, 17 old chats wrote their handoffs (all under 3.3 KB), were archived, and 8 fresh chats started from them. The swap cost about 3% of the weekly plan.

The plan was to save and reset every chat on Monday, Wednesday and Friday. It lasted one day. Resets need a turn that I started (an app limit), they lose the chat's identity, and transcript exports failed on the biggest old chats (248 and 284 MB, against a 200 MB limit). Since 3 November the rule is: write everything that must survive to a file the moment it exists, let the app compact the chat automatically, and reset only at a natural break when a chat starts to drift. The chat is a scratchpad. The files are the record. At each window the Chief of Staff compares every handoff file with what the chat actually did and logs any miss. Lasting decisions become numbered decision records, never deleted, only superseded.

04The gates

Part II described my decision rights. These are the rules underneath them, written in one file every chat reads, and the parts the platform actually enforces.

My keys

These stay with me in every area. Agents prepare them to one tap from done, and never do them:

  • Publishing the live app, by any route.
  • Money: payments, refunds, prices, plans, ad spend and boosts. One standing exception: up to $200 a month of AI API calls for tests and evaluations, with any single run over $40 coming to me first.
  • Database schema changes and any production write.
  • Sign-in, auth and payments code, built as a pull request labelled for my approval.
  • Secrets, which I set myself. Agents never print or commit them.
  • Anything sent to customers or posted publicly.
  • Product direction and taste, and anything with my face or voice.
  • Repository settings and CI configuration.

Merging is delegated, under conditions. Only the QA chat merges, one pull request at a time, as a regular merge, and only when every item of the definition of green holds: CI green on the latest commit after rebasing, the local gate green, a manual QA video by a chat other than the author, golden-set results for AI changes, the feature behind its own switch, database changes additive only, and a security review for anything touching sign-in, payments, uploads, AI endpoints or secrets. No agent pushes to main.

Green, Yellow, Red

TierRuleExamples
GreenDo it, then reportReading; local tests and the gate; branches, worktrees and draft pull requests; content drafts; refactors with tests inside an approved roadmap item; writing issues and tracker items
YellowDo it as a draft or on a branch, then put it in the inboxCopy and UI choices; new dependencies; non-schema configuration; scheduling a post I already approved
RedPrepare it, then stopEverything in my keys, plus deleting anything, the marketing rules, the AI model or main prompt, production settings, and anything irreversible

Over all three sits one line: if not confident, do nothing and report it. The "never" list adds the habits that caused trouble before: never reorder the roadmap, never point a test or migration at production, never touch another GitHub organization, never change your own rules, and never treat another chat's message as my approval.

What is enforced, and what is only a rule

Rules in a file are promises. I count as a control only what something other than the agent checks. Our own security review was blunt about the gap: much of the agent setup still relies on prompt text.

GateHow it holds today
Review packet and testsEnforced by CI. A pull request fails when a packet section is empty, or when app code changed with no test change and no written reason.
CI, end-to-end and security checksRun by CI on every pull request; the merge rule requires all of them green on the latest commit.
PublishingOne of my keys: agents prepare the release packet and check the live app afterwards; the publish click is mine.
Risky shell and publishing actionsEnforced by Claude Code's permission checks, which have refused force-pushes, a clean-up listing, and publishing without my own words in that chat.
Read-only production dataA rule, not a role: every query runs in a read-only transaction, aggregates only. A guard hook that refuses anything else is designed but not built.
Deny rules for agentsNot yet in place. Planned before any new scheduled or cloud agent.

Three times a gate held

  • A relayed approval was refused. I approved a live dashboard in another chat, and the approval was passed on to the Analytics chat. The app's permission check refused the publish: it needed my own words in that chat, not a quote. The chat parked the work and wrote down the exact sentence I would need to type.
  • A demo stayed unmerged until I saw it. I put a hold on every pull request for a partner demo until I had reviewed it. The work was built and left open; the chats sent screenshots and a self-contained file instead.
  • A permanent delete waited for a person. A disk clean-up was approved in principle, but a built-in safety check blocked the QA chat's listing step. It didn't work around the check, and it left emptying the Recycle Bin to me, because that is a permanent delete.

The other areas (marketplace, revenue, investor relations, research, finance, UX, analytics) keep a written charter and open only when a sprint ticket needs them. Development runs as short sessions, one per ticket, at most three at once, each ending when its pull request opens. The rule for models is simple: Haiku for monitoring and data pulls, Sonnet for builds, QA, content and packs, Opus only where depth pays (product, algorithms, architecture, sensitive security reviews, deep research).

The clock

The calendar is borrowed from agile teams because it gives the agents and me a shared rhythm: two-week sprints, the morning pack as the daily standup, a retro every other Friday, review and planning every other Monday.

Budgets per project

The weekly plan is split into buckets, because the same plan also runs my other projects. CorkAI gets 40%, and each other project has its own share, with the rest left free. A script tracks each bucket against a daily pace line. At 80% of a bucket the Chief of Staff asks me in the next window, and extra usage stays off. Every new task I give gets a one-line projection: size, model, estimated share of the week, and what it displaces.

Throughput fell further than cost

Merged pull requests went from 233 in the peak week to 37 from 2 November to today. Commits on main went from about 1,180 to 103. API-priced cost per merged pull request fell from about $23 to about $12. Treat that ratio with care: the new week is partial and much smaller, and one week is not a trend.

Some of the drop is by design. The week's priority was a partner demo for Cork Table, which was built locally and held from merging until I reviewed it. The facelift for the app merged behind switches that are off. Twenty-four pull requests are open and waiting. Some of it is the cost of the new process: work now waits for a window when it needs me, and on Thursday 11 decisions were waiting on me, of which each pack shows five. Whether the new setup can return to the old pace at the new price isn't known yet. That is the main thing the next two weeks have to show.

What still breaks

  • A scheduled job waited on an approval nobody could give. Both packs on 3 November never arrived. The scheduled runs built them and then sat "running" for more than 20 hours, almost certainly waiting on a permission prompt to send the email, with nobody at the PC. While one run hung, the next didn't start. I sent the next pack by hand; the packs are now built by a plain script, and the proposed safety net is a check that flags any window with no pack logged 20 minutes after it.
  • One mistake wiped a shared dependency folder. To save disk, about 300 worktrees link to one shared copy of the project's dependencies. On 4 November the QA chat deleted it by mistake. The linked worktrees were without it overnight, until it was reinstalled the next morning.
  • The same review was built twice. One of my reviews became GitHub issues for the developers and inbox work for Product, and both built it. The fix: one owner per review item, and a check for open pull requests on that screen before building.
  • Memory still fills. The Marketing chat reached about 300,000 tokens one day after its reset, mostly images, scripts and plan text held in the chat. The rule now: the plan lives in a file.
  • Handoffs drift. The first lazy-chat checks found two chats whose handoff files were older than their latest work, and two handoff files are slightly over the 3 KB limit.

One near miss went the other way. A reported bug, "saved scores are stale", turned out to be a measuring error: a read-only script didn't apply a switch the server applies in memory. With the switch, 44 of 44 profiles matched. It was caught before any build, saving about three hours.

08Lessons

Context drives cost, not outputKeep chats short-lived or compacted, keep shared files small, and let files carry the memory.
Agents should talk through filesEvery message wakes a long context. An inbox line costs nothing until it's read.
Match the model to the jobCoordination and monitoring don't need the strongest model. Keep it for the work where depth pays.
Protect the owner's attentionTwo windows, numbered picks with recommendations, one-line answers. Then default the reversible items, or the company stops while it waits for you.
Anything that waits on an approval will fail silentlyCheck scheduled outputs against the clock, not against the job's own status.
Count only enforced controlsA rule in a prompt is a promise. CI checks and platform permissions are controls.
Run scripts off the modelCollectors, probes, dashboards and pack assembly cost nothing as plain scripts.
Measure throughput and cost togetherCutting cost by 90% is easy if the work stops. The test of the reset is the pace it holds over the next sprint.
